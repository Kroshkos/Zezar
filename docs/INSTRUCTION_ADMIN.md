# Инструкция администратора — система «ЦЕЗАРЬ»

Документ для **администратора** (глобальная роль ADMIN): полный контроль над
учётными записями, подразделениями, справочниками, уведомлениями и аудитом.

---

## 1. Учётная запись администратора и вход

Единственный контур входа в систему — **логин + пароль** (страница `/login`).
Авторизация через сторонние сервисы (Яндекс ID/OAuth) полностью удалена;
приглашения по e-mail/ссылкам также отсутствуют — доступ получает только тот, кого
создал администратор.

**Env-администратор.** Первый (главный) администратор задаётся переменными
окружения:

* `ADMIN_USERNAME` (по умолчанию `admin`) и `ADMIN_PASSWORD`;
* при каждом старте сервиса сид синхронизирует эту учётную запись: если
  пользователя нет — создаёт с ролью ADMIN; если есть, но роль сбилась —
  восстанавливает ADMIN (защита от случайного понижения через API);
* несколько админов через env: `ADMIN_LOGINS=user1:pass1,user2:pass2`.

Вход env-админа выполняется на общей странице `/login` обычным логином/паролем.

Остальных администраторов/координаторов создаёт действующий администратор как
обычных пользователей с последующей сменой глобальной роли.

**Безопасность входа:**

* пароли хранятся только в виде хешей (bcrypt-style), начальный пароль
  устанавливается админом и принудительно меняется пользователем при первом входе;
* защита от перебора: не более 10 неудачных попыток с одного IP за 15 минут,
  затем временная блокировка IP (событие пишется в журнал);
* сессионная cookie живёт 14 дней, HttpOnly, SameSite=Lax, флаг Secure в
  production;
* в production приложение **не стартует** (fail-fast), если `SECRET_KEY` остался
  `change-me` или короче 32 символов, включён dev-режим или не заданы
  `ADMIN_USERNAME`/`ADMIN_PASSWORD`.

## 2. Страница «Администрирование» (системная)

Открывается из сайдбара (`/admin`). Содержит:

### 2.1 Пользователи

* **Создание:** кнопка «+» → Фамилия Имя, логин, e-mail (опционально), начальный
  пароль, глобальная роль (Участник / Руководитель / Координатор /
  Администратор). Новый пользователь обязан сменить пароль при первом входе.
* **Поиск и фильтры**: по имени/логину и по подразделению.
* **Редактирование:** ФИО, e-mail, глобальная роль, активность
  (блокировка/разблокировка). Заблокированный пользователь не может войти.
* **Сброс пароля:** задаёте новый начальный пароль — у пользователя снова
  включается принудительная смена при входе.
* **Удаление учётной записи** — с очисткой членств; карточки, где человек был
  ответственным, остаются (переназначьте ответственных заранее).
* Env-аккаунт помечен в списке особо и защищён от понижения роли (см. п. 1).

### 2.2 Подразделения (рабочие пространства)

* Создание/переименование/деактивация подразделений. Каждому пространству
  автоматически подключаются базовые модули (Дашборд, Задачи, Проекты,
  Совещания, Администрирование).
* Открыть вкладку администрирования пространства можно без параметров — система
  сама выберет пространство; переключение — селектор справа вверху.
* Состав и роли (HEAD/MEMBER) управляются со страницы администрирования
  пространства; инвариант «хотя бы один руководитель» контролируется системой:
  понижение/удаление последнего HEAD запрещено (HTTP 409 с понятным текстом).

### 2.3 Глобальные справочники

Статусы, приоритеты, типы сущностей, маршруты рабочих процессов, группы задач —
**глобальные шаблоны** (`department_id = NULL`) видны всем пространствам, где
включён соответствующий модуль. Руководители активируют их копии у себя. Меняйте
шаблоны осознанно: правки влияют на все пространства.

### 2.4 Журнал событий (аудит)

`/admin/events` — все события системы: входы/выходы, неудачные попытки и
блокировки, CRUD карточек, кадровые решения, шеринги, системные события. Фильтры
по категории и поиску, статистика. При разборе жалоб («мне поменяли роль, а
права не обновились») сверяйте время события смены роли с действиями
пользователя.

## 3. Уведомления и рассылки (Telegram)

Разделы администрирования уведомлений:

* **Сценарии уведомлений** — базовые (неотключаемые системные) и пользовательские
  сценарии: событие → кому → шаблон сообщения. Можно включать/выключать
  пользовательские сценарии, редактировать audience (получателей) и шаблоны,
  отправлять тест доставки себе.
* **Массовая рассылка (broadcast)** — текст, аудитория (всё / по подразделениям /
  по ролям), предпросмотр получателей, планирование и отмена. Очередь отправки
  видно в outbox, статус воркера — в разделе статуса.
* Настройка бота: `TELEGRAM_BOT_TOKEN` (без токена сервис работает, рассылка
  просто выключена). Пользователи привязываются сами: бот запрашивает логин и
  пароль ЦЕЗАРЬ, затем удаляет сообщения из диалога (см. INSTRUCTION_USER.md).

## 4. Интеграции и фоновые процессы

* **Яндекс Календарь (WebDAV):** воркер с периодом `SYNC_INTERVAL_SECONDS`
  (по умолчанию 300 сек) синхронизирует карточки ответственных в личные
  календари пользователей, подключивших пароль приложения. Ошибки конкретного
  пользователя (отозванный пароль — 401/403) не влияют на остальных; помогите
  пользователю переподключиться через страницу «Интеграции».
* **Long-polling Telegram** и outbox-воркер запускаются внутри приложения —
  поэтому допустим ровно **один экземпляр** сервиса (SQLite + in-process
  воркеры). Масштабирование копий с общей БД недопустимо.

## 5. Первые шаги после установки

1. Войдите под env-админом (`ADMIN_USERNAME`/`ADMIN_PASSWORD`) и смените пароль
   env-админа на стойкий (или сразу задайте его в `.env`).
2. Создайте подразделения; проверьте, что базовые модули подключены.
3. Создайте пользователей: координаторов, руководителей, участников; выдайте
   начальные пароли.
4. Назначьте руководителям роли HEAD в их пространствах (со страницы
   администрирования пространства).
5. Настройте глобальные справочники (статусы/приоритеты/типы) под регламент.
6. При необходимости настройте Telegram-бота и сценарии уведомлений.
7. Проверьте журнал событий после тестовых действий.

## 6. Диагностика типовых проблем

| Симптом | Причина / действие |
|---|---|
| Жалоба «нельзя создать карточку в своём пространстве» | Проверьте членство в пространстве; ложные срабатывания исправлены в текущей версии (проверка membership выполняется раньше глобальной роли) — обновите сервис |
| После смены роли у пользователя «старое» отображение | Права применяются мгновенно (cookie перевыпускается с новым epoch при мутации). Если наблюдается — проверьте, что запущен ровно один экземпляр с одной БД (несколько процессов с разными кэшами эпохи дают рассинхрон) |
| Не удаётся понизить последнего руководителя | Штатный инвариант: сначала назначьте второго HEAD |
| Контейнер падает на старте | Fail-fast production-правил (п. 1): SECRET_KEY, ADMIN_USERNAME/PASSWORD, DEV-флаги |
| «database is locked» | Несколько процессов пишут в одну SQLite — оставьте один экземпляр |
| Cookie слетает | Нет HTTPS / не проброшен `X-Forwarded-Proto` на прокси |
| Пользователь забыл пароль | «Сброс пароля» в списке пользователей |

Более глубокая техническая диагностика — в `INSTRUCTION_TECH.md` и `DEPLOY.md`.
