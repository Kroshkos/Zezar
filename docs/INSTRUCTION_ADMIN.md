# Инструкция администратора (ADMIN) — «ЦЕЗАРЬ»

Роль **Администратор** — полный доступ: пользователи и их пароли, глобальные
роли, подразделения, интеграции, системный аудит. Администратор входит в группу
«Координаторы» и наследует все возможности координатора
([INSTRUCTION_COORDINATOR.md](INSTRUCTION_COORDINATOR.md)).

---

## 1. Учётная запись администратора и вход

**Авторизация через Яндекс ID полностью удалена из системы.** Единственный
контур входа — **логин + пароль**.

* Главный администратор задаётся переменными окружения и синхронизируется сидом
  при каждом старте сервиса:
  * `ADMIN_USERNAME` (по умолчанию `admin`) и `ADMIN_PASSWORD` — система сама
    хеширует пароль;
  * несколько админов — `ADMIN_LOGINS=user1:pass1,user2:pass2`.
* Эта env-учётка **гарантированно имеет роль ADMIN**: даже если её случайно
  понизили через API, при следующем входе роль восстанавливается до ADMIN.
  Кнопки «Блок»/«Удалить»/«Сброс пароля» для env-админа в интерфейсе скрыты.
* Обычные пользователи (включая координаторов и руководителей) создаются вами
  в разделе «Администрирование» с **начальным паролем**; при первом входе
  пользователь обязан сменить его.

Вход: страница «Вход» → логин и пароль. Защита от перебора: 10 неудачных попыток
за 15 минут временно блокируют IP. Сессия живёт 14 дней (подписан cookie).

## 2. Общая админка (`/admin`)

Раздел **«🛡️ Администрирование»** доступен только ADMIN.

### Пользователи (`/admin/users`)

* Список всех пользователей с поиском; поля: ФИО, логин, email, Telegram-привязка,
  глобальная роль, активность.
* **«➕ Новый пользователь»** — создаёт учётную запись: Фамилия Имя, логин
  (латиница/цифры/`.` `_` `-`), email (необязательно), **начальный пароль**
  (мин. 8 символов) и роль. Передайте начальный пароль сотруднику — при первом
  входе система заставит его сменить пароль. Самостоятельная регистрация
  закрыта, приглашений по email больше нет — единственный способ доступа
  к системе — созданная вами учётная запись.
* **«✏️ Изменить»** — ФИО, email, **глобальная роль** (`member` / `coordinator` /
  `admin`). Смена глобальной роли применяется немедленно: сервер инвалидирует
  кэш прав и перевыпускает сессионный cookie пользователя с новым epoch.
* **«🔑 Сброс пароля»** — выдайте новый временный пароль; пользователь сменит
  его при входе.
* **«🚫 Блок» / «✅ Разблок»** — отключение доступа без удаления данных
  (вход выдаёт «Учётная запись заблокирована»).
* **«🗑 Удалить»** — удаление учётной записи (нельзя удалить env-админа).

> Глобальная роль ≠ роль в пространстве. HEAD/MEMBER внутри конкретного
> подразделения назначаются во вкладке «Участники» администрирования этого
> пространства (может и координатор).

### Подразделения (API `/api/core/departments`, вкладка «Подразделения»)

* **Создать подразделение** → автоматически создаётся Workspace с базовыми
  модулями (Дашборд, Задачи, Проектная работа, Совещания, Администрирование).
  Код подразделения уникален.
* Назначить руководителя пространства (добавить в состав с ролью HEAD).
* Переименовать, изменить описание, архивировать/удалять (удаление последнего
  руководителя или подразделения с участниками блокируется инвариантами).

### События / аудит (`/admin/events`)

Журнал `AuditLog`: кто, что, где и когда менял (карточки, составы, роли, шеринг,
входы в систему, блокировки IP). Фильтры по категории и поиску; отдельная
страница статистики `/admin/events/stats`. Все изменения через UI пишутся в
аудит автоматически.

## 3. Ролевая модель — шпаргалка

| Роль | Область |
|---|---|
| ADMIN | Всё + пользователи/глобальные роли/подразделения/аудит |
| COORDINATOR | Все пространства: CRUD сущностей, состав, модули, справочники, роли в пространстве, шеринг |
| HEAD | Свои пространства: состав, модули, роли в пространстве, шеринг, весь поток |
| MEMBER | Свои карточки в своих пространствах |

Системные инварианты (проверяются на уровне сервиса):

* в подразделении всегда остаётся ≥1 руководителя (HEAD) — понижение последнего
  запрещается (HTTP 409 с текстом ошибки показывается в интерфейсе); то же —
  при исключении последнего HEAD из состава;
* не более одного ответственного от каждого участвующего подразделения на сущность;
* выбор чужого пространства при создании сущности разрешён только ADMIN/COORDINATOR
  и участникам соответствующего пространства.

## 4. Интеграции

* **Telegram-бот**: `TELEGRAM_BOT_TOKEN` в `.env`; пользователи привязываются
  командой `/start <код>` со страницы «Интеграции»; уведомления — по ролевой
  области видимости; сценарии рассылки настраиваются в администрировании
  пространств (вкладка «Уведомления»).
* **Яндекс.Календарь (WebDAV)**: `YANDEX_CAL_ENABLED=true`, базовый адрес
  `YANDEX_CAL_BASE`. App-пароль CalDAV пользователь хранит сам и вводит на
  странице «Интеграции»; в БД он лежит только Fernet-шифротекстом. События
  синхронизируются детерминированными UID (идемпотентно). Статус — профиль →
  «Интеграции», отвязка — кнопкой «Отключить».
* OAuth Яндекс ID как способ входа в системе **отсутствует** (ранее удалялся —
  переменные `YANDEX_CLIENT_ID/SECRET` больше не нужны).

## 5. Безопасность и окружение

* Production fail-fast: приложение не стартует, если `SECRET_KEY` дефолтный или
  короче 32 символов, включён dev-вход (`DEV_LOGIN_ENABLED`) или демо-сид
  (`SEED_DEMO_DATA`), не задан администратор (`ADMIN_USERNAME/ADMIN_PASSWORD`).
* Session-cookie HMAC-SHA256 + флаг `Secure` за HTTPS, срок 14 суток.
* CSP/XFO/nosniff выдаются middleware; секреты — только `.env`; БД — строго
  `/data/caesar.db` (persistent volume).
* Резервное копирование `/data` — см. [DEPLOY.md](DEPLOY.md).

## 6. Частые ситуации

| Ситуация | Решение |
|---|---|
| Сотрудник не может войти | Проверьте в `/admin/users`: учётная запись создана, `is_active=true`, логин введён верно; при необходимости — «Сброс пароля» |
| «Слишком много неудачных попыток входа» | Сработала защита от перебора (10 за 15 мин на IP) — подождите или смените сеть |
| Жалоба «выбор чужого пространства» | Раньше ошибка возникала и при выборе **своего** пространства (исправлено: явный выбор пространства, где пользователь состоит, разрешён всем). Если жалоба актуальна — убедитесь, что пользователь состоит в нужном пространстве; иначе создайте задачу сами, выбрав пространство |
| Роль в пространстве «не переключилась» после смены | Исправлено: сервер перевыпускает cookie с новым `acl_epoch` в ответе мутации, права применяются сразу после перезагрузки. Если видите старую роль: обновите страницу; проверьте, что операция не отклонена (409: нужен другой HEAD — текст ошибки показывается в интерфейсе); при нескольких воркерах убедитесь, что БД одна |
| Нужно понизить последнего руководителя | Сначала назначьте нового HEAD, затем понижайте старого (понизить себя можно, если в пространстве уже есть другой руководитель) |
| Env-админ потерял роль ADMIN | Не страшно: при следующем входе сид/логика входа восстановят роль ADMIN из `ADMIN_USERNAME` |
