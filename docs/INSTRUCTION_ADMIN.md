# Инструкция администратора (ADMIN) — «ЦЕЗАРЬ»

Роль **Администратор** — полный доступ: пользователи, глобальные роли,
подразделения, приглашения, интеграции, аудит. Администратор входит в группу
«Координаторы» и наследует все возможности координатора
([INSTRUCTION_COORDINATOR.md](INSTRUCTION_COORDINATOR.md)).

---

## 1. Общая админка

Раздел **«🛡️ Администрирование»** (`/admin`) доступен только ADMIN. Вкладки:

### Пользователи (`/admin/users`)

* Список всех пользователей: имя, Яндекс-ID, email, Telegram-привязка, глобальная
  роль, активность.
* **Пригласить пользователя** — по email/Яндекс-аккаунту; пользователь войдёт через
  Яндекс ID и получит доступ к указанным пространствам. Регистрация закрыта —
  допуск только из списка админа или по invite.
* Изменить: `display_name`, `email`, **глобальную роль** (`member` / `coordinator` /
  `admin`), `is_active` (блокировка/разблокировка), вручную привязать/снять
  `telegram_chat_id`.
* Смена глобальной роли применяется немедленно (кэш прав инвалидируется, сессия
  пользователя переиздаётся).

> Глобальная роль ≠ роль в пространстве. HEAD/MEMBER внутри конкретного
> подразделения назначаются во вкладке «Участники» администрирования этого
> пространства (может и координатор).

### Подразделения (`/admin/departments` / API `/api/core/departments`)

* Создать подразделение → автоматически создаётся Workspace с базовыми модулями
  (Дашборд, Задачи, Проектная работа, Совещания, Администрирование).
* Назначить руководителя пространства (добавить в состав с ролью HEAD).
* Переименовать, архивировать/удалять.

### События / аудит (`/admin/events`)

Журнал `AuditLog`: кто, что, где и когда менял (карточки, составы, роли, шеринг).
Все изменения через UI пишутся в аудит автоматически.

## 2. Ролевая модель — шпаргалка

| Роль | Область |
|---|---|
| ADMIN | Всё + пользователи/роли/подразделения/приглашения/аудит |
| COORDINATOR | Все пространства: CRUD сущностей, состав, модули, роли в пространстве, шеринг |
| HEAD | Свои пространства: состав, модули, роли в пространстве, шеринг, весь поток |
| MEMBER | Свои карточки в своих пространствах |

Системные инварианты (проверяются на уровне сервиса):

* в подразделении всегда остаётся ≥1 руководителя (HEAD) — понижение последнего
  запрещается (HTTP 409 с текстом ошибки показывается в интерфейсе);
* не более одного ответственного от каждого участвующего подразделения на сущность;
* выбор чужого пространства при создании сущности разрешён только ADMIN/COORDINATOR
  и участникам соответствующего пространства.

## 3. Интеграции

* **OAuth Яндекс ID**: credentials задаются в `.env` (`YANDEX_CLIENT_ID/SECRET`,
  redirect URI). Без них production-запуск не стартует.
* **Telegram-бот**: `TELEGRAM_BOT_TOKEN`; пользователи привязываются командой
  `/start <код>`; уведомления — по ролевой области видимости.
* **Яндекс.Календарь**: CalDAV/WebDAV, app-пароль пользователя хранится
  Fernet-зашифрованным; события синхронизируются детерминированными UID
  (идемпотентно). Статусы синхронизации — в профиле → «Интеграции».

## 4. Безопасность и окружение

* Production fail-fast: короткого/дефолтного `SECRET_KEY`, включённого dev-входа
  или демо-сида приложение не допускает.
* Session-cookie HMAC-SHA256 + `Secure` за HTTPS; CSP/XFO/nosniff из middleware.
* Секреты — только `.env`; БД — строго `/data/caesar.db` (persistent volume).
* Резервное копирование `/data` — см. [DEPLOY.md](DEPLOY.md).

## 5. Частые ситуации

| Ситуация | Решение |
|---|---|
| Сотрудник не может войти | Проверьте: пользователь создан/приглашён, `is_active=true`, Яндекс-ID совпадает |
| Жалоба «выбор чужого пространства» | Убедитесь, что пользователь состоит в нужном пространстве; иначе создайте задачу сами, выбрав пространство |
| Роль в пространстве «не переключилась» после смены | Обновите страницу; если не помогло — проверьте, что операция не отклонена (409: нужен другой HEAD) |
| Нужно понизить последнего руководителя | Сначала назначьте нового HEAD, затем понижайте старого |
